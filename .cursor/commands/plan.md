## Задача

Думай **глубоко, системно и многослойно**, как архитектор и тимлид.

При анализе:
- задавай себе вопросы: **"почему?"**, **"что если?"**, **"что пойдет не так?"**
- ищи:
    - скрытые зависимости
    - неочевидные сценарии
    - edge-cases
    - влияние на существующую систему

> ❗ **Запрещено писать код. Только анализ и планирование.**

---

## 🔍 Анализ задачи

1. Проанализируй задачу / сервис
2. Определи:
    - бизнес-цель (зачем это делается)
    - входные данные
    - выходные данные
    - ключевые сценарии использования (happy path + edge cases)
3. Выдели:
    - изменяемые компоненты
    - новые компоненты
4. Определи:
    - зависимости (внутренние / внешние)
    - контракты (API, события, БД)
5. Опиши риски:
    - технические (нагрузка, консистентность, race conditions)
    - архитектурные (tight coupling, scaling limits)
    - интеграционные (внешние сервисы)
6. Определи влияние на стандарты:
    - STANDART_CODE.md
    - STANDART_TEST.md
    - STANDART_JAVADOC.md
    - STANDART_SWAGGER.md
    - STANDART_DOCKER.md
    - STANDART_LIQUIDBASE.md (если есть БД изменения)

---

## 🧠 Проектирование решения

### Обязательно:

- Определи **все эндпоинты**
- Для каждого:
    - HTTP метод
    - URL
    - request/response
    - валидацию
    - бизнес-правила
    - ошибки (включая edge cases)

### Дополнительно (УЛУЧШЕНИЕ):

- Определи:
    - идемпотентность (если применимо)
    - транзакционные границы
    - необходимость retry / fallback
    - необходимость кэширования
    - влияние на SLA / производительность

## 🏗 Стратегия реализации

План должен быть:

- **декомпозированным**
- **проверяемым (через acceptance criteria)**
- **независимым по эндпоинтам**
- **готовым к параллельной разработке**

---

## 📋 Структура плана

### 1. Анализ и проектирование

- Анализ требований
- Проектирование API
- Проектирование данных (DTO / Entity)
- Выделение общих компонентов
- Определение Liquibase-изменений

---

### 2. Общая инфраструктура (один раз)

> Только то, что переиспользуется

- Entity
- Repository
- Liquibase (если нужно)
- Общие DTO
- Mapper (без endpoint-specific методов)
- Validator (без endpoint-specific методов)
- Service interface (без endpoint-specific методов)
- Конфиги
- Docker (если требуется)

---

### 3. Реализация по эндпоинтам

> ⚠️ Каждый эндпоинт — вертикальный slice (от DTO до тестов)

Для **каждого эндпоинта**:

#### 3.1 DTO
- Request / Response
- Валидация
- Swagger Schema

#### 3.2 Mapper
- Методы маппинга
- Особые случаи

#### 3.3 Validator
- Бизнес-валидация
- Ошибки

#### 3.4 Service
- Бизнес-логика
- Транзакции
- Вызовы зависимостей

#### 3.5 Controller
- API интерфейс
- HTTP коды
- Валидация

#### 3.6 JavaDoc
- Полное покрытие методов и DTO

#### 3.7 Unit тесты
- Service
- Validator
- Mapper

#### 3.8 Integration тесты
- MockMvc
- Проверка всех сценариев

#### 3.9 Swagger
- Документация
- Примеры ответов
- Ошибки (RFC 7807)

---

### 4. Финализация

- README (на русском)
- Проверка стандартов
- Проверка Docker
- Проверка backward compatibility

## 🆕 Добавленные улучшения (ключевое)

### 1. Контроль качества плана

Каждая задача должна содержать:

- четкое описание
- **acceptance criteria**
- проверяемый результат

---

### 2. Edge cases (обязательно)

Для каждого эндпоинта учитывать:

- невалидные данные
- отсутствующие ресурсы
- конфликты
- гонки (race conditions)
- повторные запросы

---

### 3. Архитектурные проверки

В конце плана добавить:

- нет ли дублирования логики
- можно ли выделить переиспользуемые компоненты
- не нарушается ли SRP / SOLID
- нет ли избыточной связанности

---

### 4. Нефункциональные требования

Обязательно учитывать:

- производительность
- масштабируемость
- отказоустойчивость
- логирование
- мониторинг

---

### 5. Готовность к продакшену

Проверить:

- health checks
- метрики
- логирование
- конфигурации
- безопасность (валидация, доступы)

---

### 6. Ретроспектива (новое)

Добавить в план:

- анализ реализации
- выявленные проблемы
- предложения по улучшению
